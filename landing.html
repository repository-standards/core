Why it exists

Knowledge never lives where the work happens.

Four failure modes, each one you have watched happen. The standard exists to kill them - by keeping the knowledge in the repo, versioned with the code.

01

Decisions evaporate in chat

The why behind a choice lives in a Slack thread or an agent session, then it is gone - so the next person re-litigates a decision that was already made.

02

Docs rot away from code

A wiki that lives elsewhere drifts the moment the code changes. Nobody trusts it, so nobody updates it, so it drifts further.

03

Specs describe, they don't build

A spec you cannot rebuild or verify from means the code is the only real truth - and the spec quietly starts to lie.

04

Drift goes unnoticed

Code and intent diverge silently. You find out in an incident, not in a review - when it is expensive instead of cheap.

The mechanism

One versioned standard. One align mechanism. Three moments.

Adopting, updating, and staying compliant are the same operation at different starting points - not three tools you wire together.

01 Adopt

Point & align

A new or existing repo is read, compared to the target version, and brought into line - adapted to its own stack, never blind-copied.

02 Update

Bump the version

Already on v0.7.1? Read the delta to v0.7.2 and apply just that - the way copier update or a dependency bump works, not a re-scaffold.

03 Verify

Drift as a number

The version ships a manifest; self-verify checks the repo against every entry and reports drift - drift 0 or the build fails. A number your CI asserts and a fleet owner can sort on.

Who it's for

Four ways in. Same standard underneath.

Whether you're starting clean, rescuing a mess, shipping features with an agent, or keeping a fleet current - you're using one versioned standard.

03

What's inside

Knowledge that lives next to the code.

Not a wiki that rots. Everything the standard installs is a file in the repo, read by humans and agents alike.

AGENTS.md # single entry point, agents-first specs/ # living capability specs README.md # by capability, buildable capability-map.json decision-records/ adr/ # technical decisions (MADR) bdr/ # business decisions catalog.md # which decisions to make backlog.md # the work, agent-first skills/ # spec-*, onboard-repo, align guards/ # structure, coupling, secrets
specs/

Living capability specs

Behavior organized by capability, not by ticket or page - and buildable, not just described. The spec stays the source of truth after merge; a guard keeps it coupled to the code.

adr · bdr

Decision records + a catalog

Technical (ADR) and business (BDR) decisions in MADR format - plus a catalog of the forks every project hits, with an opinionated default for each.

backlog.md

A backlog that feeds itself

Items arrive from spec deltas, code↔spec drift, and onboarding - and leave only when their definition of done is met.

guards/

Enforcement, not prose

Dependency-free, zero-install checks: self-verify scores drift against the version's manifest; reflect keeps the assembled skeleton in sync with source; a coupling guard binds each spec to its code; secrets are scanned. The “verify” step, mechanized.

How you work

Specify. Detail. Build. Repeat.

Three roles, one living spec. The spec travels between them, gaining precision at each hand-off - and the loop never ends: every change starts the cycle again. The AI never invents behavior or an unrecorded decision.

  • Description
  • Features & rules

Detail

Raise it to buildable; record the decisions a change forces.

  • Details & contracts
  • Implementation shape
  • Decisions (ADR / BDR)
→
AI agent

Build

A plan from the spec, then code + tests until spec = code = tests.

  • Plan from the spec
  • Build & test
  • Reconcile, then ship
specify → detail → build ↻ and around again - continuous work, not a one-way pipeline.
