The spec

The whole standard is one page. Read it in three minutes.

standard/SPEC.md is the entire normative core: numbered rules on one page, numbers stable - the tooling cites them. The manifest is the spec's machine-readable projection; self-verify scores your repo against it. No hundred-page handbook to interpret.

The mechanism

One versioned standard. One align mechanism. Three moments.

Adopting, updating, and staying compliant are the same operation at different starting points - not three tools you wire together.

01 Adopt

Point & align

A new or existing repo is read, compared to the target version, and brought into line - adapted to its own stack, never blind-copied.

02 Update

Bump the version

Already on v0.7.1? Read the delta to v0.7.2 and apply just that - the way copier update or a dependency bump works, not a re-scaffold.

03 Verify

Drift as a number

The version ships a manifest; self-verify checks the repo against every entry and reports drift - drift 0 or the build fails. A number your CI asserts and a fleet owner can sort on.

Two paths in

Greenfield or brownfield. Same standard underneath.

Where you start doesn't change where you end up. And you don't stop at the method: the align router detects your technology and offers the registered best practices for it - stack repos, official when listed in the registry.

01
Greenfield

Start clean

Scaffold from the standard at a pinned version and go - specs, decisions, guards and the agent guide are wired in from commit one.

$ scaffold from repository-standards@0.7.2
02
Brownfield

Rescue a messy repo

Assess, align, onboard - in prioritized waves, not a big-bang rewrite. Re-enter the loop wave after wave until drift hits zero. A years-old, messy repo is a first-class citizen here, not a lost cause.

$ assess → align → onboard
03
PO · Architect · Dev

The PO writes the story

A PO writes a story in plain language - no code required. The loop walks them through clarifying questions; technical ones can be explicitly deferred. The spec reaches ready-to-develop only through that gate, so developers and the AI build from a contract, not from vibes.

story → clarify → ready-to-develop → build
04
Team · Standard owner

Keep a fleet current

Cut a new version of the standard and every repo can update to it - one repo or a hundred - each self-verifying that it actually complies.

$ update me to repository-standards@next

What lands in your repo

Knowledge that lives next to the code.

Not a wiki that rots. Everything the standard installs is a file in the repo, read by humans and agents alike - and AGENTS.md at the root is the entry an agent executes: it reads, loads the skills and guards, aligns, specs, records, verifies.

AGENTS.md # single entry point, agents-first SPEC.md # the whole standard - one page of rules .standards-version # the pin standard.manifest.json # what compliant means, as data specs/ # living capability specs README.md # by capability, buildable capability-map.json # spec <-> code coupling docs/decision-records/ adr/ # technical decisions (MADR) bdr/ # business decisions docs/backlog.md # the work, agent-first .claude/skills/ # 11 skills - the loop, executable scripts/ # self-verify, guards, the spec engine
specs/

Living capability specs

Behavior organized by capability, not by ticket or page - and buildable, not just described. The spec stays the source of truth after merge; a guard keeps it coupled to the code.

adr · bdr

Decision records + the checklist

Technical (ADR) and business (BDR) decisions in MADR format - plus a checklist of the forks every project hits, with an opinionated default for each.

backlog.md

A backlog that feeds itself

Items arrive from spec deltas, code↔spec drift, and onboarding - and leave only when their definition of done is met.

scripts/

Enforcement, not prose

Dependency-free, zero-install checks: self-verify scores drift against the version's manifest; a structure guard keeps specs shaped and owned; a coupling guard binds each spec to its code; secrets are scanned. The “verify” step, mechanized.

Who it's for

Specify. Detail. Build. Forever.

Three roles, one living spec, on an endless loop. Each change goes around again - specify -> detail -> build - so the spec stays the truth and the work never dead-ends. The AI never invents behavior or an unrecorded decision.
